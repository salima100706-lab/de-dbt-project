# Аналитический слой интернет-магазина (dbt)

Проект dbt для построения аналитических витрин по схеме «звезда» на основе сырой OLTP-базы магазина.

### Витрины и их зернистость

| Витрина | Зернистость | Бизнес-вопрос |
| :--- | :--- | :--- |
| **fct_orders** | Заказ | Сколько заказов и на какую сумму сделали за месяц? |
| **fct_order_items** | Товар в заказе | Какая выручка по категориям товаров и брендов? |
| **dim_customers** | Клиент (включая не купивших) | Сколько денег приносит один клиент (в разрезе городов и каналов)? Какая доля клиентов вообще совершает покупки? |
| **dim_products** | Товар | К какой категории и верхнему уровню (Home/Electronics) относится товар? |
| **dim_dates** | День | Сколько денег принесла конкретная дата? Как выручка менялась по дням и месяцам? |

### Хранение в Greenplum
| Витрина | Материализация | Распределение (distributed_by) | Ориентация | Обоснование |
| :--- | :--- | :--- | :--- | :--- |
| **fct_orders** | `table` | `order_id` | `column` | Большая таблица, частые фильтры по номеру заказа. Колоночное хранение ускоряет агрегации. |
| **fct_order_items** | `table` | `order_id` | `column` | Большая таблица, JOIN с заказами по `order_id`. Колоночное хранение для аналитики. |
| **dim_customers** | `table` | `distributed_replicated=true` | — | Маленькая таблица-справочник. Копируется на все сегменты для быстрых JOIN. |
| **dim_products** | `table` | `distributed_replicated=true` | — | Маленькая таблица-справочник. Копируется на все сегменты. |
| **dim_dates** | `table` | `distributed_replicated=true` | — | Маленькая таблица-справочник. Копируется на все сегменты. |

### Доп задание: инкрементальная модель fct_order_items

Модель `fct_order_items` сделана инкрементальной (`materialized='incremental'`, `unique_key='order_id'`).
Она добавляет только новые заказы, у которых `order_date` больше максимальной даты в текущей таблице.

**Какие изменения такая модель пропустит:**
1. **Изменение статуса существующего заказа.** Если заказ был создан и загружен вчера, а сегодня его статус изменился на "cancelled", инкрементальная модель этого не увидит, так как `order_date` у заказа не изменился
2. **Удаление заказов из источника.** Если заказ удалили из OLTP-базы, он останется в витрине навсегда
3. **Опоздавшие данные (late-arriving data).** Если заказ был создан в прошлом месяце, но загрузился в базу только сегодня, он не попадет в витрину, так как его `order_date` меньше текущей максимальной даты
4. **Изменение суммы или количества товара в существующей позиции.** Если в заказе поменяли количество или цену, инкрементальная модель это пропустит
